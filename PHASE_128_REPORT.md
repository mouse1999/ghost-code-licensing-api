# Phase 128 — Secure Licensing API Foundation: Report

**Outcome: implemented as a separate project, partly verified. NOT production-ready, and the Spring Boot layer has never been compiled or started.**
Environment: Linux sandbox, JDK 21.0.12, Maven 3.9.11 with **no reachable Maven Central** (policy block, same as Phase 127), no Spring/JUnit/H2/JDBC-driver jars, PostgreSQL 16 server + `psql` available.

## 1. Architecture and changed files
`licensing-api/` is a standalone Maven project beside `interview-assistant/`. **No file of the desktop application was changed.**
Baseline confirmed from Phase 127: Spring Boot 4.1.0, Java 21, Maven, package root `com.interviewassistant`, secrets kept out of source/config, env-var overrides.
The new project mirrors those choices (parent `spring-boot-starter-parent:4.1.0`, `com.interviewassistant.licensing.*`).

Design choice: the security-critical logic is **framework-free Java** (so it could be compiled and executed here); Spring is a thin shell.
* `domain` (immutable records + `LicenseStatus` state machine) · `crypto` (activation codes, Ed25519/JWS, device proofs, PEM, key ring) · `security` (admin auth, rate limiter, nonce cache) · `store` (port + plain-JDBC implementation + transaction runner) · `service` (issuance, client, admin) · `web` (Spring: controllers, DTOs, filters, error handler, properties, wiring) · `tools` (`AdminTokenTool`, `KeyGenTool`).
* 62 source files / ~6,000 lines (main + tests + SQL + docs). Full list: see the zip.
* Admin authentication is a path-prefix servlet filter (not Spring Security) — smaller surface, deny-by-default, and no dependency on Security 7 APIs I could not compile against.

## 2. Database and migrations
* PostgreSQL in production; Flyway locations `db/migration/common` (**V1**: `license`, `activation_credential`, `device_registration`, `issuance_request`, `audit_event`) and `db/migration/{vendor}` (**V2 postgresql**: triggers that reject UPDATE/DELETE/TRUNCATE on `audit_event`).
* DB-enforced: credential hash unique and one per license; device key unique per license; `CHECK active_device_count <= device_limit`; status/limit/validity/window checks; e-mail stored lower-case; `ACTIVE` requires `activated_at`; foreign keys everywhere.
* Atomic operations: `reserveDeviceSlot` = one conditional `UPDATE … WHERE status IN (PENDING,ACTIVE) AND active_device_count < device_limit`; lifecycle changes use an optimistic `version` check.
* Tests use H2 (PostgreSQL mode) via `JdbcLicenseStoreIT`; differences from production: embedded engine, different locking implementation, no V2 triggers.

## 3. Endpoints
Documented field-by-field with dummy examples, status codes, error codes, auth and idempotency in `docs/API.md`.
Admin: issue (idempotent via `Idempotency-Key`), get, find by e-mail, suspend, reinstate, revoke, audit (per license / global, cursor paging). Client: activate, validate, entitlement (renew), public key set. **Device reset is deferred** (schema/columns ready).

## 4. Admin authentication and secrets
Static 256-bit bearer tokens (`ia_adm_…`), generated by `AdminTokenTool`, shown once; only the SHA-256 is configured. Constant-time comparison across all credentials, per-credential scopes (`LICENSE_ISSUE`, `LICENSE_READ`, `LICENSE_LIFECYCLE`, `AUDIT_READ`), failed-attempt throttling, deny-by-default on `/api/v1/admin/**`. No secret has a default value; start-up fails without pepper, signing key (outside dev), admin credential and DB settings. Limitations: `docs/SECURITY.md` §2.

## 5. Entitlement signing and rotation
JWS compact, `alg: EdDSA` (Ed25519, JDK-native), `kid` header, claims `ver, iss, jti, lic, dev, dkt, rights, iat, exp, ren, lexp`. Private key only on the server (mode-600 check, pair self-test at start-up, no accessor). Strict verifier. Rotation by key id with a verify-only directory: `docs/KEY_ROTATION.md`. A signature never overrides revocation: validate/renew read the database each time.

## 8. Known security limitations and deployment requirements
See `docs/SECURITY.md` (12 items). Highlights: minimal admin auth (no MFA/users); in-memory per-process rate limits and nonce cache; application-level audit immutability only (DBA can alter; `REVOKE` privileges and export logs); stolen unredeemed code + e-mail can activate first; offline behaviour and local key protection belong to Phase 129. Requirements: run `mvn verify` first; PostgreSQL with a least-privilege role; TLS-terminating proxy with correct trusted-proxy setting; secrets from a secret store; NTP; backups.

## 9. Deferred to Phase 129 (and later)
Desktop activation screen, device key generation and local private-key protection, offline grace/renew policy and server-validation schedule, embedding public keys in the desktop build, enforcement across `LIVE`/`AI_LIVE`/`DSA`/`SCREEN_QUESTION`, device reset (needs authorisation/cooldown design), admin edits of an existing license (limit/rights/expiry), shared rate-limit state if scaled out, real admin identity (users/MFA) if the admin surface grows.

## Decisions for your review
1. **Spring Security not used** for admin auth (path-prefix filter instead). Say if you prefer Spring Security.
2. **Device reset deferred.** The contract and schema are ready.
3. **Reinstate** endpoint added (the state machine needs SUSPENDED→ACTIVE/PENDING; only suspend/revoke were requested).
4. Activation code is reusable until `device_limit` devices are bound (so retries and multi-device licenses work), not single-use.
Phase 129 should not start until this report has been reviewed, as instructed.
